# Разработка More Boosty

[README](README.md) · [English README](README.en.md) · [Правила для агентов](AGENTS.md)

Для разработки нужны Node.js 24 и npm. Минимальная поддерживаемая версия Node.js — 22.13.

```sh
npm ci
npm test
npm run release
```

Результат: папка `distribution/` для установки в браузер, `release.zip` для стора
и `artifacts/` с версионным ZIP, SHA256SUMS и заметками релиза.
После изменения кода пересоберите расширение, перезагрузите его на `chrome://extensions`
и обновите вкладку Boosty.

## Коммиты

Используем [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```text
type(scope): short imperative description
```

Scope необязателен. Заголовок — на английском, до 100 символов.
Один коммит описывает одно законченное изменение.

| Тип | Когда использовать |
| --- | --- |
| feat | Новая возможность |
| fix | Исправление ошибки |
| refactor | Изменение устройства кода без новой функции |
| perf | Улучшение производительности |
| docs | Документация |
| test | Тесты |
| build | Сборка и зависимости |
| ci | GitHub Actions |
| style | Форматирование кода |
| chore | Обслуживание проекта |
| revert | Отмена изменения |

Примеры: `fix(ui): handle players with delayed shadow roots`,
`build(deps): update esbuild`, `docs: add English installation guide`.
Для несовместимого изменения используйте `!` после типа/scope или footer `BREAKING CHANGE:`
с описанием миграции.

Чтобы включить проверку сообщений локально:

```sh
git config core.hooksPath .githooks
```

Хук не требует сторонних пакетов. Автоматические merge-коммиты Git допускаются.
CI отдельно проверяет заголовок pull request; для squash merge он должен следовать той же нотации.
Проверки применяются к новым изменениям, старую историю не переписываем.

## Changelog и версии

Заметные для пользователя изменения добавляйте в обе языковые части `[Unreleased]` файла
[CHANGELOG.md](CHANGELOG.md). Включайте только готовое поведение, исправления и изменения обработки данных.

Для подготовки версии:

```sh
npm version 1.0.1 --no-git-tag-version
```

npm обновит `package.json` и `package-lock.json`; lifecycle-скрипт `version` синхронизирует
`source/manifest.json`. Затем перенесите готовые записи в раздел
`## [1.0.1] - YYYY-MM-DD` и оставьте пустой `[Unreleased]` для следующих изменений.
Релизные заметки должны содержать `### Русский` и `### English`.

## Релиз на GitHub

1. Обновите версию и changelog. Выполните `npm test`, `npm run release` и `git diff --check`.
2. Закоммитьте изменения, например `chore(release): prepare v1.0.1`, и включите их в `main`.
3. Создайте аннотированный тег на этом коммите и отправьте его:

```sh
git switch main
git pull --ff-only
git tag -a v1.0.1 -m "More Boosty v1.0.1"
git push origin v1.0.1
```

Для первой версии нового цикла используйте `v1.0.0`; выше приведён пример следующего обновления.
Workflow Release проверит, что коммит входит в main, тег совпадает с версией, а changelog содержит
датированные заметки. После тестов и сборки создаётся GitHub Release с
`more-boosty-vX.Y.Z.zip` и `SHA256SUMS`. Текст релиза берётся из changelog на русском и английском.
Записи из старой истории в него автоматически не подтягиваются.

Проверка и сборка выполняются с read-only токеном; право записи есть только у job публикации.
Проверки и релизы выполняются на общих GitHub runners Ubuntu.
Для повторной публикации существующего тега можно вручную запустить Release в Actions,
выбрать ветку `main` и указать тег в поле `tag`. Будет собран именно этот тег.
Достаточно стандартного `GITHUB_TOKEN`, отдельный PAT не нужен.
Опубликованную версию не перезаписывайте: исправление выпускайте с новым номером.
Если создание релиза завершилось ошибкой после его появления на GitHub, сначала проверьте
имеющиеся assets; не повторяйте публикацию вслепую.

Публикация в Chrome Web Store выполняется отдельно по [инструкции](docs/publishing.md).
